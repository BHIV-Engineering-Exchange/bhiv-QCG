# Platform Generic Capability Invocation Contract

This document outlines the deployed canonical generic capability invocation endpoint and contract for a service registered in the TANTRA Platform Registry. It covers the request/response schema, authentication, version negotiation, dispatch semantics, and evidence/replay linkage.

The entire orchestration logic is housed primarily within `platform_capability_sdk.py` and the schemas are defined in `sdk_models.py`.

---

## 1. Deployed Invocation Endpoint

The invocation endpoint is **dynamically resolved**. When a service registers, it defines an `execution` url under `endpoints`. 

```json
"endpoints": {
    "execution": "https://<service-host>/api/v1/execute"
}
```
The SDK looks up the service from the registry, extracts `endpoints.execution`, and executes a `POST` request to it. (Fallback testing mock endpoints reside at `POST /platform/v1/services/{service_id}`).

---

## 2. Request Payload Schema

When the `invoke_capability()` method fires, it sends a standardized `POST` JSON request wrapped by the SDK:
```json
{
    "service_id": "TANTRA-PSR-USF-001",
    "operation": "discover_solvers",
    "payload": { ... },                // Dynamic parameters for the operation
    "version": "1.1.0",                // The negotiated compatible version
    "invocation_id": "a7b2dfe8-..."    // A unique UUID generated by the SDK
}
```

---

## 3. Response & Error Schema (`InvocationResult`)

The invocation returns an immutable, deterministically hashable `InvocationResult` object:
```json
{
    "invocation_id": "a7b2dfe8-433e-43eb-9044-da445803f9a9",
    "service_id": "TANTRA-PSR-USF-001",
    "operation": "discover_solvers",
    "status": "SUCCESS",            // Enums: SUCCESS | FAILED | TIMEOUT | CIRCUIT_OPEN | VERSION_REJECTED | SERVICE_NOT_FOUND
    "response": { ... },            // The raw capability payload returned
    "duration_ms": 142.5,
    "trust_method": "CLASSICAL",    // CLASSICAL | HYBRID | POST_QUANTUM
    "evidence": { ... },            // Cryptographic evidence linkage (see Section 7)
    "error": null,                  // Populated string if status != SUCCESS
    "retry_count": 0,
    "timestamp": "2026-08-08T15:15:00Z"
}
```

---

## 4. Authentication 

Authentication is deeply tied to `ServiceIdentityProvider` and `TrustProvider`. The SDK injects the active capability's identity token into the invocation request to assure mutual authentication, passing `trust_method` claims across boundaries (e.g., CLASSICAL, POST_QUANTUM).

---

## 5. Version Negotiation

The SDK mandates strict version compatibility *before* the capability is ever dispatched:
1. `negotiate_version(service_id, version)` is called.
2. If `UNSUPPORTED`, the invocation fails fast with a `VERSION_REJECTED` status.
3. If `COMPATIBLE` or `DEPRECATED`, the exact negotiated version bounds are injected into the HTTP Request Payload.

---

## 6. Dispatch Semantics

Execution logic is handled defensively inside the SDK loop:
* **Circuit Breakers**: Before making the network call, it checks a breaker threshold (`allow_request()`). Repeated failures transition the service to `CIRCUIT_OPEN`.
* **Retries & Backoff**: Configurable exponential backoff retries for transient networking failures (default: 3 attempts).

---

## 7. Evidence & Replay Linkage

To satisfy TANTRA’s zero-trust requirement, every capability invocation natively generates an `InvocationEvidence` record:
1. The SDK calculates a `request_hash` (hashing the `payload`) and a `response_hash`.
2. This is packaged with the `invocation_id` into an `InvocationEvidence` record.
3. The SDK appends this to its internal `EvidenceChain` (which hashes `previous_hash` + `current_hash` for immutability).
4. The Replay Authority (`federated_validation_suite.py`) guarantees that duplicate `invocation_id`s or mutated payloads matching the same execution chain are deterministically rejected.
